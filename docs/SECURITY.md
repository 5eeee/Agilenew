# Безопасность и приватность

## Реализованные меры

- Пароли хэшируются `bcrypt` с cost 12 и никогда не возвращаются клиенту.
- Сессии случайные, в базе хранится только их хэш; cookie — `HttpOnly`, `Secure`, `SameSite=Strict`.
- Токен восстановления подписан HMAC, живёт 30 минут и становится недействительным после смены пароля.
- Ответ восстановления одинаков для существующего и неизвестного email, поэтому адреса пользователей нельзя перебирать.
- Изменяющие запросы проверяют `Origin` и ограничиваются по IP и назначению.
- Профиль и аватар валидируются; размер data URL ограничен.
- Заказ, этап и отзыв всегда проверяются на принадлежность текущему пользователю.
- Отзыв доступен только после статуса `COMPLETED`.
- Установлены HSTS, запрет MIME sniffing, frame policy, referrer и permissions policies.
- SMTP и webhook-секреты читаются только из переменных окружения и исключены из Git.
- Неиспользуемые API чатов, звонков, компаний и хранилища удалены из публичной сборки.
- `npm audit --omit=dev` выполняется в CI.

## Персональные данные

Собираются только данные, необходимые для договора и сопровождения заказа: имя, email, необязательный телефон/аватар, состав заказа, этапы согласования и отзыв. В логи нельзя писать пароли, session cookie, reset tokens, SMTP credentials или полное содержимое персональных сообщений.

## Production checklist

1. Задать `AGILE_PASSWORD_RESET_SECRET` длиной не менее 32 случайных байт.
2. Задать `AGILE_SMTP_*`, используя отдельный пароль приложения почтового ящика.
3. Ограничить `AGILE_EMAIL_TO` рабочим корпоративным адресом.
4. При подключении платформы задать отдельный `AGILE_ORDER_WEBHOOK_SECRET` и HTTPS URL.
5. Делать резервные копии PostgreSQL и проверять восстановление минимум раз в квартал.
6. Просматривать audit/dependency PR и Vercel logs перед каждым production-релизом.
